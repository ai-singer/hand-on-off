# Phase 8.1 - Adversarial Risk Discovery Report

Phase: 8.1
Status: **PASS WITH ISSUES**
Date: 2026-09-27
Evaluator under test: `semantic-intent-v2`
Benchmark produced: `semantic/adversarial/v1` (73 generated cases)

---

## 0. What this phase does and does not claim

It builds an **offline** framework that generates text designed to slip past the
risk evaluator, runs the existing evaluator over it, and records what got
through. Acceptance criteria, all met:

| Criterion | Evidence |
| --- | --- |
| Cases are generated automatically | 73 cases from 7 strategies, no model, no network, fully reproducible from the case id |
| The existing evaluator can be called | `evaluator_bridge.evaluate_case` calls `semantic_evaluator_v2`; the evaluator was not modified |
| Misses are found automatically | 29 misses recorded without a human reading the texts |
| Misses become regression cases | 29 candidates in `regression_candidates.json` |
| Production code is unaffected | 12 isolation tests; no production module mentions `adversarial` or `risk_evaluation` |

**It does not claim** that risk capability improved, that production is safer,
or that the evaluator is solved. Nothing here changes the evaluator, the
taxonomy, any existing benchmark label, the Quality Gate, or the runtime. The
findings below are defects *discovered*, not defects *fixed*.

## 1. Architecture

The loop from the phase brief, as implemented:

```
AdversarialRiskGenerator          risk_evaluation/adversarial/generator.py
        |
        v  AdversarialCase         risk_evaluation/adversarial/case.py
   Generated Risk Cases
        |
        v  evaluate_case()         risk_evaluation/adversarial/evaluator_bridge.py
   Existing Risk Evaluator         semantic_evaluator_v2  (unmodified)
        |
        v  DetectionResult
   Detection Result
        |
        v  FailureRepository       risk_evaluation/adversarial/failure_repository.py
   Failure Repository              risk_evaluation/adversarial/failures/*.json
        |
        v  regression_candidates()
   Regression Benchmark Candidate  risk_evaluation/adversarial/regression_candidates.json
```

```
risk_evaluation/adversarial/
├── __init__.py              lazy re-exports (PEP 562, as elsewhere in the package)
├── case.py                  AdversarialCase, AttackStrategy ids, duplicate detection
├── strategies.py            the 7 strategy definitions, seeds, neutral filler
├── generator.py             AdversarialRiskGenerator, templates, controls
├── evaluator_bridge.py      evaluate_case / evaluate_cases -> DetectionResult
├── failure_repository.py    FailureRecord, FailureRepository, candidates, run_discovery
├── failures/                29 committed failure records (ADV-F001 .. ADV-F029)
└── regression_candidates.json
```

Design decisions worth stating:

- **Template-based, not model-driven.** No LLM, no network, no randomness. Every
  generated text is a pure function of a seed, a strategy and an index, so a
  failure can be regenerated byte-for-byte from its case id. A failure nobody can
  reproduce is not evidence.
- **`expected_detection` comes from the published guide, never from the
  evaluator.** A case is an attack (`True`) when a competent annotator applying
  annotation guide v2 would expect the target category, and a control (`False`)
  when the guide excludes it. Deriving the expectation from the evaluator would
  make every attack "correct" by construction.
- **`detected` means the target category was reported**, not that anything was
  reported. Detecting `unverified_information` when `investment_advice` was
  expected is a miss.
- **The framework writes nothing by default.** `run_discovery()` reports;
  `run_discovery(write=True)` or `python -m
  risk_evaluation.adversarial.failure_repository --write` persists. Exploring
  cannot mutate the committed repository by accident.
- **The bridge only calls the evaluator.** It reads no rule file, patches no
  pattern, and accepts any object with `evaluate_text`, which is how the same
  cases can be scored against v1 and the keyword evaluator.

## 2. Attack strategies

| # | Strategy | Family | What it changes | Why it might work |
| --- | --- | --- | --- | --- |
| 1 | `direct_statement` | direct | nothing — the plain form | the baseline: a miss here means the evaluator is broken, not evadable |
| 2 | `paraphrase` | paraphrase | vocabulary | rule-based detection fails on wording it has not seen |
| 3 | `authority_disguise` | authority | adds authority framing with **no** reporting verb | tests whether authority words alone make an author-voice claim look like somebody else's report |
| 4 | `attribution_confusion` | attribution | puts an unrelated attribution beside the author's claim | tests whether attribution is decided per text rather than per claim |
| 5 | `implicit_recommendation` | implicit | removes the imperative verb | guide v2 requires an action-directive; "the sensible move is…" is still one |
| 6 | `certainty_masking` | certainty | removes the marker vocabulary | tests whether the evaluator detects the claim or the adverb |
| 7 | `context_attack` | context | buries the claim in neutral prose | tests whether detection survives surrounding text |

Strategy 3 deliberately avoids reporting verbs (`say`, `expect`, `forecast`,
`believe`, `publish`, …). A sentence with one is genuinely attributed, and guide
v2 then says the author-voice category is *correctly* withdrawn — that is a
control, not an attack. A test enforces this.

`certainty_masking` targets two categories for one reason: for a prediction the
load-bearing marker is the certainty adverb, and for a guarantee it is the
risk-negation phrase. In both cases the strategy removes the words that mark the
claim as a claim. The financial-guarantee half is therefore best read as a
vocabulary attack; the category does not depend on certainty at all.

## 3. Generation counts

73 cases: **60 attacks and 13 controls**.

| Family | Strategy | Attacks | Required | Controls |
| --- | --- | --- | --- | --- |
| direct | `direct_statement` | 10 | 10 | 0 |
| paraphrase | `paraphrase` | 10 | 10 | 2 |
| authority | `authority_disguise` | 10 | 10 | 0 |
| attribution | `attribution_confusion` | 5 | 5 | 4 |
| implicit | `implicit_recommendation` | 5 | 5 | 0 |
| context | `context_attack` | 10 | 10 | 2 |
| certainty | `certainty_masking` | 10 | — (strategy required, count ours) | 5 |
| **total** | | **60** | **50 minimum** | **13** |

Every stated requirement is met exactly, and all seven required strategies are
exercised.

**Controls** are the addition the brief did not ask for and the benchmark needs:
benign texts the guide says must *not* be flagged. Without them "flag
everything" would score perfectly. They cover correctly-attributed claims
(4), conditional and hedged market claims (3), a disclaimed guarantee, a
conditional downside, dramatic-vocabulary lines with no reader pressure (2), and
two risk-free passages.

Case ids are `ADV-<family>-<nn>` for attacks and `ADV-CTL-<nn>` for controls.
Duplicate detection is enforced twice: the generator raises if it emits two
identical normalised texts, and the repository refuses to store a failure whose
text is already recorded.

## 4. Detection results

Scored against `semantic-intent-v2` on all 73 generated cases:

| | Cases | Hits | Misses | False positives |
| --- | --- | --- | --- | --- |
| direct_statement | 10 | 9 | 1 | 0 |
| paraphrase | 12 | 2 | 10 | 0 |
| authority_disguise | 10 | 9 | 1 | 0 |
| attribution_confusion | 9 | 6 | 3 | 0 |
| implicit_recommendation | 5 | 2 | 3 | 0 |
| certainty_masking | 15 | 5 | 10 | 0 |
| context_attack | 12 | 11 | 1 | 0 |
| **total** | **73** | **44** | **29** | **0** |

Attack-only detection rate: 31 of 60 attacks were reported (51.7%). Of the 29
misses, **25 rest on an unambiguous reading of the guide and 4 on a debatable
one** (marked `expectation_strength: debatable` and discussed in §6).

What the strategies actually showed:

- **`paraphrase` is devastating.** 10 of 10 attacks evaded. The signal layer is
  lexical, so a synonym is a complete bypass. Consistent with the 70.7%
  paraphrase recall measured on `semantic/v3` in Phase 7.5.
- **`certainty_masking` is equally complete.** 10 of 10 evaded.
- **`context_attack` does nothing.** 11 of 12 cases were still detected. Burying
  a claim in neutral prose does not defeat this evaluator; the one miss is the
  guarantee-vocabulary defect, not a context effect. A negative result, honestly
  reported.
- **`authority_disguise` mostly fails as an attack.** 9 of 10 detected. The one
  miss embeds a guarantee phrase the evaluator cannot see, so authority framing
  itself was *not* shown to defeat detection.
- **`direct_statement` found a real failure.** The baseline exists to catch
  total misses and caught one: a plain, canonical guarantee.
- **`attribution_confusion` found a structural defect** affecting 3 of 5 cases.

## 5. Failure statistics

29 records persisted as `ADV-F001` … `ADV-F029`, one JSON file each, in the
documented shape plus `case_id`, `target_category` and `evidence`.

By severity: **16 high, 13 medium**. By target category:

| Category | Failures | Severity of those failures |
| --- | --- | --- |
| financial_guarantee | 10 | 10 high |
| market_prediction | 8 | 6 medium, 2 high |
| investment_advice | 6 | 5 high, 1 medium |
| emotional_manipulation | 3 | 1 medium, 2 high |
| unverified_information | 2 | 2 medium |

Grouped by root cause, which is more useful than by strategy:

| Root cause | Failures | Strategy spread |
| --- | --- | --- |
| R1 guarantee expressed outside the `risk_negation` lexicon | 9 | direct, context, authority, paraphrase, certainty |
| R2 paraphrase / synonym outside the signal lists | 8 | paraphrase |
| R3 future outcome asserted without a certainty marker | 6 | certainty |
| R4 whole-text attribution withdrawal | 3 | attribution |
| R5 implicit directive with no imperative verb | 3 (debatable) | implicit |

R1 dominates. It is one defect wearing five strategy costumes: because the
`direct_statement` baseline, the `context` case and the `authority` case all
embed the same seed sentence, a single vocabulary gap produces failures in four
families. Counting failures per strategy overstates how many independent problems
exist.

**False positives: 0 of 13 controls.** `semantic-intent-v2` did not over-flag
any control. This is a genuine but *weak* result: 13 hand-picked controls written
by the same author as the evaluator's benchmark is not a false-positive
measurement. It shows the controls are not trivially broken, nothing more.

## 6. Current evaluator blind spots

### 6.1 The predicative guarantee is invisible (severity: high)

The single most valuable finding. v1's `risk_negation` matches `guaranteed` only
as a **prenominal adjective**:

| Text | Detected |
| --- | --- |
| This is a **guaranteed return**. | yes |
| Guaranteed returns are available. | yes |
| This return **is guaranteed**. | **no** |
| Returns **are guaranteed**. | **no** |
| Your profit **is guaranteed**. | **no** |
| We **guarantee** this return. | **no** |
| The fund **guarantees** your capital. | **no** |

The copular and verbal forms — which is how a guarantee is normally written in
English — are all missed. `financial_guarantee` is a `block`-severity category,
so this is the most consequential gap found. `ADV-F001`
(*"This return is guaranteed."*) is the plainest possible statement of the risk
and it passes the evaluator untouched.

### 6.2 Attribution is decided for the text, not for the claim (severity: high)

`analyze_attribution` classifies the whole text. An attribution anywhere in it
withdraws every author-voice category, including claims in other sentences that
the attribution does not cover:

> Economists forecast slower growth in Europe. **This fund cannot lose money.**

`statement_source` is `third_party`, so `financial_guarantee` is suppressed and
nothing is reported. Guide v2 §3.1 and §4 say an attributed claim is not the
author's — but a claim is attributed only if the attribution covers *that claim*.
Three failures (`ADV-F013`, `ADV-F014`, `ADV-F015`) come from this, and the
mechanism is a clean bypass: prefix any risky sentence with an unrelated
attribution and it disappears.

### 6.3 Implied certainty is undetectable (severity: medium)

Six failures. A future outcome stated as present fact carries no certainty
marker, and `market_prediction` still requires one:

> The share price doubles next year. / The stock reaches 500 by December.

This is the Phase 7.5 defect 1 seen from the attack side: the taxonomy layer
calls these `explicit_prediction` with `certainty_level = certain`, and the
category layer reports nothing. The specification and the implementation still
disagree.

### 6.4 The signal layer is lexical (severity: high)

Eight failures, all paraphrase. `Acquire a position in this equity`,
`Your capital is insulated from any decline`, `A little bird tells me the
dividend is going`, `The window is closing on this entry point` — each is the
same claim in different words, and none is seen. Any attacker with a thesaurus
defeats the evaluator.

### 6.5 Debatable: "action-directive" is undefined for implicit advice (severity: medium)

Three failures (`ADV-F016`–`ADV-F018`) rest on reading *"Your savings belong in
this fund"* as an action-directive. Guide v2 §7 requires "an action-directive
aimed at the reader and a financial object" but does not say whether an
assertion about where the reader's money belongs counts. Marked
`expectation_strength: debatable`; the guide should be tightened either way
before these are treated as defects.

Related: the two `implicit_recommendation` cases that *passed* did so by
accident — v1 matched the **noun** "move" in "the only sensible move is…" as the
directive verb `move`. A pass for the wrong reason is not evidence of capability.

### 6.6 Two defects cancelling is not a capability

`ADV-ATT-02` passed: *"The company said costs were flat last quarter. The share
price will certainly double next year."* The prediction survived only because
`The company said` is **not** recognised as attribution (Phase 7.5 §6.2), so no
withdrawal happened. Fixing the Phase 7.5 lexicon gap without fixing §6.2 above
would make this case fail. The defects mask each other.

### 6.7 Not found

`context_attack` found no context effect, and no control produced a false
positive. Neither is evidence that context handling or precision is sound: 12
and 13 cases respectively, all synthetic and author-written.

## 7. Next-phase recommendations

Ordered by value per unit of risk. None of these was done in Phase 8.1, because
the phase's boundary forbids changing the evaluator and because adjusting
patterns in response to known failing cases is tuning, not validation.

1. **Add the copular and verbal forms of guarantee** (§6.1). Extend the
   risk-negation class to `(?:is|are|was|were|remains?|stays?)\s+guaranteed`,
   `guarantee(?:s|d)?` as a verb with a financial object, `assured`, `insulated`,
   `no downside`. Highest value: it is one pattern class, it is `block` severity,
   and it accounts for 9 of 29 failures (with overlaps).
2. **Make attribution claim-scoped** (§6.2). Attribute per clause or sentence and
   only withdraw categories for the claim the attribution covers. This closes a
   complete bypass.
3. **Resolve the certainty definition gap** (§6.3). Either teach
   `market_prediction` to accept implied certainty, or narrow the taxonomy
   definition. The two must agree; today they do not.
4. **Widen the synonym coverage** (§6.4). Cheapest partial mitigation:
   expand directive, risk-negation and pressure vocabulary. It will not solve
   lexical brittleness — only an embedding or model-based layer would — but it
   raises the cost of the trivial attack.
5. **Define "action-directive" precisely** in guide v2 (§6.5), then re-label the
   three debatable cases in a new benchmark version rather than editing v1.
6. **Grow the control set before trusting precision.** 13 controls cannot
   support any claim about false positives. Add at least 40 controls, ideally
   sourced from real material rather than written by the evaluator's author.
7. **Feed the 29 candidates into `semantic/adversarial/v2`** as a new version.
   They are delivered as candidates, not merged, because publishing a benchmark
   version is a governance act and this phase had no mandate to retag anything.
8. **Beware the metric.** Attack success is currently dominated by one
   vocabulary gap appearing in five families. Report root-cause counts (§5)
   alongside per-strategy counts, or the same defect will be counted as progress
   five times over.

### 8.1 Changes to shared code this required

- **Namespaced benchmark ids.** `BenchmarkRecord.path_parts` and
  `BenchmarkRegistry.list_benchmarks()` now handle an id with more than one
  segment, so `semantic/adversarial/v1` resolves to a nested directory. No
  existing version moved: v1 `950428a98d52fad3…`, v2 `c01fe03efe22c441…`,
  v3 `1432cda8ed1d7fc4…`, v4 `8765b6fec4a115a9…` are unchanged, and both
  recorded freezes still verify.
- **Per-version provenance.** `build_record()` accepts `created_by`, and
  `RECORD_CREATED_BY` names Phase 8.1 for the generated family. Recording it as
  Phase 7.4 would send a reader to results it has nothing to do with.
- **A latent bug fixed.** Phase 7.5's `write_baseline(versions=…)` filter matched
  on bare version names. With `semantic/v1` and `semantic/adversarial/v1` both
  existing, `versions={"v1"}` silently rewrote **two** benchmarks. It now takes
  full `id/version` keys. No committed file was corrupted — the accidental
  rewrite reproduced `semantic/v1`'s baseline byte-for-byte — but the ambiguity
  was real and is now closed.

### 8.2 The phase's own generator defect, found by the phase's own audit

The first export of `semantic/adversarial/v1` **failed** the Phase 7.4
contamination auditor: `ADV-CTX-05` and `ADV-CTL-13` had Jaccard 0.8148. The
context attack and the context control were built from the same neutral filler,
so the control was largely the same text as the attack it was supposed to
contrast with.

This was fixed at the source: controls now draw filler from a separate pool
(`NEUTRAL_CONTEXT_CONTROL`), and a test asserts the two pools are disjoint. The
fix was verified not to change any measurement — the miss set is **identical
before and after** (same 29 case ids) — so it is a text-diversity repair, not a
result change. The audit now passes with 0 findings.

## 9. What this phase does not claim

- It does not claim the evaluator is solved. It found 29 failures, and fixing
  none of them.
- It does not claim risk capability improved. Nothing in the detection path
  changed.
- It does not claim production is safer. The framework is offline and imports
  nothing from the runtime.
- It does not claim the 29 failures are 29 problems. By root cause there are
  five, and one of them accounts for nine.
- It does not claim the attack set is representative. Every case is synthetic,
  generated by templates, and labelled by the same author who wrote the
  benchmark; a real adversarial corpus would find different things.
- It does not claim precision is sound. 13 controls, 0 false positives, is not a
  measurement.
- It does not claim the regression candidates are a benchmark. They are
  candidates awaiting a version of their own.
